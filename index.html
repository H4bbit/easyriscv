Introduction

In this tiny ebook you will learn bare-metal RISC-V assembly by drawing pixels, looping counters, and building a Snake game — all in the widgets embedded in each chapter. Each widget is a little RV32I assembler and simulator: assembly goes in the textarea, pixels come out on the 32x32 canvas.

How to use a widget: click Assemble, then Run. Tick Debugger and press Step to execute one instruction at a time while watching the registers. Tick Monitor to watch a slice of memory. Hexdump shows the assembled bytes, Disassemble shows what the CPU decodes, Notes reminds you of the memory map.

Every chapter teaches two forms of each instruction: first the canonical RV32I instruction (what the hardware executes), then immediately its assembler pseudo-instruction (what the programmer writes). The disassembly is the proof — it shows only canonical encodings.

Numbers and Immediates

Before writing code, a quick note on numbers. RISC-V assemblers understand decimal and hex. Hex is prefixed with 0x:

  • 42 decimal
  • 0x2A hex — same value, 42
  • 0x200 hex = 512 decimal — our framebuffer base
  • 0xF = 15 decimal — max color nibble

If you are not familiar with hex, read the Wikipedia article. Hex digits are 0-9 A-F. Each digit is 4 bits, each byte is two digits (0x00-0xFF), each word is eight digits.

Immediates vs Memory

In li t0, 5, the 5 is an immediate — a value encoded directly in the instruction. In sw t0, 0(t1), the 0 is an offset added to the base register t1.

li is a pseudo-instruction. For small values (-2048 to 2047) it is just one instruction: addi t0, zero, imm. Larger values need two: lui t0, hi + addi t0, t0, lo. You will see both forms in the disassembly from the next chapter on.

Words

All RISC-V registers are 32 bits (4 bytes). pc advances by 4. Our memory is words at 0x000, 0x004, 0x008... but we can still store single bytes with sb.

Stepping Through

Reset, tick Debugger, and Step while watching the registers:

  1. addi t0, zero, 1 — loads 1 into t0. RISC-V has 32 32-bit registers; adding to zero is the canonical way to load a small constant.
  2. addi t1, zero, 0x200 — t1 = 0x200.
  3. sb t0, 0(t1) — stores the low byte of t0 at t1+0 (0x200). Rows are 32 bytes wide: 0x200-0x21F is row 0, next row starts at 0x220. Only the low 4 bits are the color.

Then the same idea in shorthand: li t0, 5 / li t0, 8 (each is addi from zero). pc starts at 0x600 and advances by 4 per instruction.

Why This Matters

On real hardware video is more complex, but the idea is the same: memory-mapped I/O. Writing to 0x200 is not plain RAM — the display interprets it as a pixel. Plain RAM is the zero page at 0x00 (used in later chapters).

Registers

You have seen t0 and pc change. What do they mean? The debugger panel shows the register file:

  • zero (x0) — always 0. Use it to compare against zero (beq rs, zero, label) or as source for li.
  • ra (x1) — return address for jal.
  • sp (x2) — stack pointer. You set it yourself (li sp, 0x1FC).
  • t0-t6 — temporaries, scratch values.
  • s0-s11 — saved registers (s0 is also fp).
  • a0-a7 — arguments and return value.

There is no flags register. Branches do the compare directly (see Branching). A full list of the RV32I instruction set is in the RISC-V ISA Manual, Volume I: Unprivileged, the RISC-V Assembly Programmer’s Manual, and the RISC-V Green Card. Keep them open beside the debugger — they are your bible.

Memory

RISC-V uses a simple load/store model. Every memory access is a lw/sw (or lh/lb/lbu/sh/sb) with base + 12-bit immediate: 0(t0) or 4(t0). For indexing, compute the address first: add t3, t0, t2; sw t1, 0(t3).

The Stack

Jumping

RISC-V has two jump forms: jal and jalr.

  • jal rd, label — rd = pc+4; pc = label. jal ra, func calls a function, jal x0, label is an unconditional jump (j), jal x0, 0 is an infinite loop halt.
  • jalr rd, offset(rs1) — rd = pc+4; pc = rs1+offset & ~1. jalr zero, 0(ra) returns (ret pseudo).

jal/jalr never touch the stack: ra is just a register. A nested jal overwrites it, so a function that calls another must save ra first (for example with sw ra, 0(sp)) and restore it before returning — the save is your code’s own convention, and removing it breaks the outer return (try it in the Jumping chapter below).

outer:
    addi sp, sp, -4
    sw ra, 0(sp)
    jal ra, inner
    lw ra, 0(sp)
    addi sp, sp, 4
    ret

ALU

RISC-V arithmetic is three-operand with no flags: the result goes to a register, and the next instruction decides what to do with it. This chapter tours the whole integer ALU — logic, shifts, compare — using the canvas as a truth table. It assumes you can dice and mask (see IO).

Logic: AND / OR / XOR

Each bit is computed independently:

  • and — 1 where both are 1. Used as a mask: andi t1, t1, 0x03 keeps only the low 2 bits, turning 0-255 into 0-3.
  • or — 1 where either is 1. Used to combine: 0x0A | 0x05 = 0x0F (15).
  • xor — 1 where they differ. Used to toggle: xori t6, t6, 0x0F flips the low nibble (0xFF becomes 0xF0, low nibble 0).

Register-register (and/or/xor) and immediate (andi/ori/xori) forms both exist.

Shifts and compare

  • slli t4, t2, 2 — shift left by 2 = ×4. This is how the next chapter scales an index to words, and how Snake computes y*32 (slli t3, t3, 5). Right shifts: srli (zeros in) vs srai (sign bit in).
  • slt t5, t3, t4 — 1 if t3 < t4 (signed), else 0. Branches like blt do this compare internally; slt keeps the 0/1 in a register instead. sub is the matching counterpart of add.

Base + index×4

Word arrays need scaling: element i lives at base + i*4. Three instructions do it — shift, add, store:

  1. slli t4, t2, 2 — i × 4 (<< 2 is the ×4 you met in ALU)
  2. add t5, s0, t4 — address = base + offset
  3. sw t3, 0(t5) — store the word

Tick Monitor (start 0) and Run: RAM shows 0 1 1 2 3 5 8 13. Each loop iteration appends one word. Final a0=13, same value as before — the storage is new.

Overall structure

After the .equ constants, the first block is:

    jal ra, init
    jal ra, loop

init initializes the game state, and loop is the main game loop. The loop subroutine itself just calls subroutines sequentially before looping back:

loop:
    jal ra, read_keys
    jal ra, check_collision
    jal ra, update_snake
    jal ra, draw_apple
    jal ra, draw_snake
    (spin delay)
    j loop

Zero-page usage

Game state lives in zero-page RAM at 0x00: direction at 0x00, segment count at 0x04, apple pixel address at 0x08, then one word per segment from 0x0C (head first). Directions use one bit each: 1=up, 2=right, 4=down, 8=left — opposite pairs share one AND test, so reversal is rejected.

The game loop

Reading the input

read_keys loads 0xFF (ASCII of the last key) and compares it to 0x77 (w), 0x64 (d), 0x73 (s), 0x61 (a). Each direction first checks the current one: moving down while pressing up is illegal, so the snake cannot reverse into itself.

Collision and movement

check_apple grows the snake by one segment and places a new apple when head meets apple. check_snake ends the game when the head meets any body segment. update_snake shifts segments tail-ward (seg[i] = seg[i-1]) and moves the head one cell, with wall checks on all four sides — without input the snake walks right into the wall and halts red at game_over.

Rendering

draw_apple paints the apple in a random color, draw_snake erases the tail (black) and paints the head white. The apple position comes from two 0xFE reads masked to 5 bits (X 0-31, Y 0-31, Y*32+X via slli) — the whole 32x32 screen is playable because code lives far away at 0x600.

Memory map

0x000-0x0FF  RAM / zero-page (variables, game state)
0x100-0x1FF  stack (grows down from 0x1FC)
0x200-0x5FF  framebuffer 32x32, 1 byte/pixel (low nibble = colour)
0x600-...    code (PC starts at 0x600)
0xFE/0xFF    MMIO random / last-key (intercepted on LOAD)
0x1000       MMIO print-char port (intercepted on STORE)

Assembler notes

  • Two passes (define/.equ, labels, then code at 0x600. Fixed 32-bit words, so every instruction is 4 bytes except li with a large immediate (lui + addi, 8 bytes).
  • Canonical first, pseudo right after: li/mv/nop/j/jal/jr/ret, not/neg/seqz/snez/sltz/sgtz, beqz/bnez/blez/bgez/bltz/bgtz, bgt/ble/bgtu/bleu all assemble to their canonical encodings. Disassembly shows the same folds as llvm-objdump and the C VM on the main branch (nop/li/mv/not/neg/seqz/snez/sltz/sgtz/beqz/bnez/blez/bgez/bltz/bgtz/j/jal/jr/jalr/ret).
  • li takes a number or symbol only: a label address needs la (auipc + addi); call is jal when near, tail is j when near (everything fits in our fixed 0x600 4KB model).
  • Comments are # (also // and ; for old sources). Numbers are decimal, 0x hex, $ hex, % binary. .byte/.word emit raw data.
