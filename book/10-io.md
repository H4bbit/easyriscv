# IO

So far every program was closed: same input, same output. Now let's meet
the VM's outside world — three memory-mapped ports and one syscall.

Run:

```bash
just debug 10-io
```

Source (`labs/10-io/prog.s`):

```asm
    li t0, 0xFE
    lbu t1, 0(t0)      // random 0-255
    andi t1, t1, 0x0F
    sb t1, 0(t2)       // FB[0] = random color
    li t0, 0x1000
    sw t1, 0(t0)       // prints char to stdout
    li a0, 33          // '!'
    li a7, 1
    ecall              // prints a0 as char
```

## The four doors

| Address | Name | Direction | Meaning |
|---------|------|-----------|---------|
| `0xFE` | random | read | new random byte on every instruction |
| `0xFF` | last key | read | ASCII of last key pressed (`0` if none) |
| `0x1000` | print-char | write | low byte of stored word goes to stdout |
| `ecall` (`a7=1`) | print-char | syscall | low byte of `a0` goes to stdout |

`0xFE` is how games roll dice: mask it down (`andi t1, t1, 0x0F` for `0-15`,
`andi` + `addi` for a range like `2-5`). Headless runs print real randomness —
run `just run 10-io` twice and `FB[0]` differs.

`0xFF` is how games read input: compare against `$77` (`w`), `$64` (`d`),
`$73` (`s`), `$61` (`a`). In `just debug`, pressing a key stores its ASCII
there; headless it stays `0`.

`0x1000` and `ecall` both print, by different mechanisms: a store to an
address outside RAM is intercepted by the VM, while `ecall` traps with the
convention `a7=1, a0=char` (the only syscall this VM implements — there is
no OS, no `read`, no `exit`; `j .` halts).

## Try It

Step through `10-io` headless and watch stdout: it prints `OK!`. In debug
mode, press keys and watch `mem[0xFF]` change in `w_mem`; the lab's
exercise 3 turns a keypress into a pixel.
